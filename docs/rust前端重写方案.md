结论：**工程不算“小改”，但也不是推倒全部重写。**  
你现在这个项目后端已经是 Rust/Tauri，真正要重写的是 `src/` 前端：我粗看了一下，大约 **32 个前端文件、约 5900 行 TS/TSX/CSS**。功能集中在时间轴、搜索、截图预览、设置、统计、条目编辑这些地方。**属于中等规模重写**。

## 能不能把内存压到 100MB 以下？

**可以尝试，但要明确：如果继续用 Tauri/WebView，100MB 以下很难稳定保证。**

Tauri 官方定位是用系统 WebView 做“小、快、安全”的跨平台应用，前端仍然是 Web 技术栈。它比 Electron 轻，但 WebView 本身在 Windows 上会有独立进程和渲染开销。Tauri 官方也说明它支持任意前端框架，前端是 WebView 方案。  
来源：Tauri 官方首页称其使用 OS native web renderer，并支持 Web 前端栈。https://tauri.app/

如果目标是 **整个应用运行时常驻内存 <100MB**，我建议不要再用 React/Tauri WebView 做 UI，而是改成 **原生 Rust GUI**。

## 推荐方案

### 首选：Slint

我更推荐 **Slint + 现有 Rust 后端逻辑**。

原因：

- Slint 是 Rust/C++/JS/Python 可用的声明式 GUI 框架；
- 官方强调 UI 会编译成机器码；
- 官方写明 Slint runtime 可低到 **小于 300KiB RAM**，适合低资源场景；
- 对桌面、嵌入式、移动端都有支持。  
来源：Slint 官方首页。https://slint.dev/

这个项目的时间轴、分类、设置页、统计面板，用 Slint 重写比较合适。

### 备选：egui

**egui** 也可以，尤其适合你的时间轴这种高度自定义绘制界面。它是 Rust immediate mode GUI，原生运行，不依赖 WebView。  
来源：egui GitHub。https://github.com/emilk/egui

缺点是复杂表单、弹窗、样式体系可能不如 Slint 直观，最终 UI 质感可能更偏工具软件。

### 不太推荐：Dioxus Desktop

Dioxus 是 Rust 的跨平台/fullstack 框架，也支持 desktop/mobile/web。  
来源：Dioxus 官网。https://dioxuslabs.com/

但如果 desktop 方案仍然走 WebView，那对“压到 100MB 以下”的帮助有限。

## 我建议的路线

不要一上来全量重写，建议分三步：

1. **先测当前内存来源**
   - 区分 Tauri 主进程、WebView2 子进程、截图缓存、React 状态、图片预览。
   - 如果只是截图缩略图/缓存导致，可能不用重写。

2. **做 Slint/egui 小原型**
   - 只实现一天时间轴 + 条目列表 + 当前计时。
   - 接入现有 SQLite 查询。
   - 测空闲内存、截图后内存、一天数据多时内存。

3. **如果原型稳定低于 100MB，再迁移全 UI**
   - 先迁移主时间轴；
   - 再迁移设置、搜索、统计；
   - 最后移除 React/Tauri 前端。
